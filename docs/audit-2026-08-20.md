**Overall.** The assembly product is complete and stable through its whole pipeline: edit, validate, build to five distribution routes, package, launch, export. The BASIC work has delivered its foundations, its naming model, and its command routing, and stops short of an executable BASIC pipeline. The gap between what the extension now advertises for BASIC and what it can actually do is the single most important item on this list.

### Three corrections to the status section of the requirements document

**1. Test composition is misreported.** The document records 45 assembly, 48 language/parser, 40 routing. Actual composition:

```
assembly            45   dialect 10, project 12, manifest 14, template 9
BASIC language      31   lexer 21, metadata 10
routing / actions   57   evidence 13, language 16, resolver 28
                   ---
                    133
```

**2. xbas99 IS wired into the build coordinator.** The document lists this as not implemented. It is implemented, at `src/toolchain/profiles.ts:196`:

```
'basic-program': args: ['${tool}/xbas99.py', '-c', '${input}', '-o', '${output}']
```

It runs today and produces the tokenised loader on the Extended BASIC assembly disk. What is missing is not tokenisation. What is missing is a project whose *primary language* is BASIC: `basicSource` is currently a secondary input to an assembly project, and the routing layer intercepts BASIC targets before the coordinator is reached. That is a smaller gap than the document implies, and it is a different gap.

**3. Auto-run LOAD behaviour is verified, not outstanding.** Proven twice from a cold Classic99 start and recorded in `docs/basic-support-design.md` section 1.9. A standard-format PROGRAM named LOAD auto-loads and auto-runs; the long INT/VAR 254 format does not. The `xb-autorun-disk` target may be advertised on that basis.

### Two findings this audit adds

**BASIC files have no syntax highlighting.** `ti-basic` and `ti-extended-basic` are registered as languages with a language configuration, but no TextMate grammar exists for either. Opening a `.b99` file today shows plain unstyled text. The language registration makes the extension look responsible for those files while providing nothing visible.

**Show Memory Map does not show a memory map.** The command loads the `.equ` symbol file and focuses the Symbols view. That is a symbol table. Requirement 29.2 asks for address ranges, segments, reserved regions and overlap detection, and none of that model exists. The command name promises the requirement and delivers something else.

## 6. Prioritised gap list

### P0 - correctness and safety

1. **BASIC languages are registered without grammars.** A `.b99` or `.xb99` file opens as unstyled text under a TI language mode. The extension claims the file type and provides nothing. Either ship grammars or unregister the languages until the parser lands.
2. **`Show Memory Map` does not produce a memory map.** It focuses the symbol view. Rename the command to match what it does, or build the model in requirement 29.2. Misleading command names cost user trust.
3. **embed-xb compatibility is undetected.** A local xdt99 patch was applied during development for payloads over 257 bytes. A user with unpatched xdt99 3.6.5 building an `xb-loader` target gets a corrupt artifact with no diagnostic. Requirement 50.5 forbids patching their install, so detection plus a clear message is the required behaviour.

### P1 - core product functionality

4. BASIC parser, AST and binder. Everything in requirements 55 to 61 waits on it.
5. BASIC as a project language: `language: "ti-basic"` should select the tokenisation pipeline for a project whose entry source is BASIC.
6. BASIC disk packaging and the three declared BASIC disk targets.
7. Standard versus long format selection, with long used only when required.
8. BASIC Build and Run reaching a real emulator launch.
9. Complete the metadata inventories: statements, functions, operators, keywords, and confirm the four entries flagged `confirm`.
10. Detokenisation, the prerequisite for all of phase 2.
11. Published JSON Schema for `ti99.json`, with `jsonValidation` so the file gets IntelliSense.

### P2 - high-value IDE functionality

12. BASIC completion, hover, signature help, semantic highlighting.
13. Round-trip: import from disk, source-versus-disk diff, update on disk.
14. Disk browser write operations.
15. Extension-host tests for the Quick Pick flows, closing acceptance items 7 and 15.
16. Signature help and semantic tokens for assembly.
17. Renumbering and label mode.
18. Build environment report and support bundle.
19. Synchronised listing navigation.

### P3 - future

20. SDK, hardware profiles, SAMS, TIPI, DSR layer, graphics and sound studios, debugger, C, GPL, Forth, retro core.

## 7. Named findings

**A. Project file name differs from the specification.** The spec says `ti99-project.json` throughout; the implementation uses `ti99.json`. The implementation name is shorter and already shipped in a released version and in the project template. Recommendation: update the specification rather than the code, and record the decision.

**B. No JSON schema.** Requirement 12.2 asks for a published schema with IntelliSense. `ti99.json` is hand-edited today with no completion or validation. Low effort, high daily value, and it should be authored deliberately rather than generated from the current interfaces.

**C. Assembly extensions were narrowed.** From `.a99 .asm .s .inc .equ` to `.a99 .asm`. `.s` is the standard GNU and ARM assembler extension, so claiming it meant anyone with this extension installed could get TMS9900 highlighting and TMS9900 diagnostics on unrelated files. Users who want the old behaviour can add `files.associations`. This is a deliberate deviation from requirement 22.1.

**D. BASIC grammars missing.** See P0 item 1.

**E. embed-xb patch is not reflected in product behaviour.** See P0 item 3. The development machine has a patched xdt99; a user machine will not.

**F. No extension-host tests.** Requirement 36.5 asks for the official VS Code test framework. The resolver is deliberately free of `vscode` imports so most logic is testable without a host, which covers 14 of the 16 acceptance criteria in requirement 150. The two that remain are the source-selection Quick Pick behaviours, and they genuinely need a host.

**G. Memory map is a symbol table.** See P0 item 2.

## 8. Verification plan for items marked Needs Verification

**embed-xb compatibility (50.5).** On a machine with stock xdt99 3.6.5, build the `xb-loader` target for a payload over 257 bytes. Expected today: a silently truncated or malformed program. Required: a diagnostic naming the xdt99 version and the affected payload size. Compare against the patched install used in development, whose backup is `xas99.py.bak-before-embedxb-fix`.

**Marketplace publisher.** Attempt `vsce login kenfitz`. Expected: failure until the publisher is registered at the Marketplace management portal. Nothing else blocks first publish.

**Acceptance items 7 and 15.** Open a workspace with two runnable entry sources and run `TI-99: Build and Run` from the Command Palette with no editor focused. Expected: a Quick Pick listing both with their resolved languages. Then open an ambiguous `.bas` and confirm the dialect question appears before any build action.

**Cross-platform.** No macOS or Linux run has occurred. Path handling is normalised and tested, but toolchain discovery order differs per platform and has never been executed there.

## 9. Bibliography additions

Sources used during implementation that the requirements bibliography does not list. Grouped to match its existing structure.

### B. TI BASIC and Extended BASIC

- **xdt99 `doc/EMACS.md` and `ide/README.md`** - the only xdt99 documents that map file extensions to languages. They are the evidence that `.b99`, `.bas` and `.xb` all resolve to one BASIC mode, which is what makes `.b99` a weak presumption rather than a dialect statement. Not in the manual, and easily missed.
- **`xbas99.py` default output extension, line 854** - `ext='.b99'`. The reason the import pipeline must choose its own filename rather than accept the tool default.
- **AtariAge, Question about non-TI filesystem extensions for TI BASIC files** - https://forums.atariage.com/topic/309621-question-about-non-ti-filesystem-extensions-for-ti-basic-files/ - the community discussion of `.bas` versus `.xb` versus other conventions. Note: AtariAge returns HTTP 403 to automated fetching, so this needs a human reader.
- **Ninerpedia, Extended BASIC** - https://www.ninerpedia.org/wiki/Extended_BASIC - checked for an extension convention; it documents none, which is itself evidence.
- **arcadeshopper TI-99/4A FAQ, Extended BASIC** - https://www.arcadeshopper.com/wp/ti-99-4a-faq-extended-basic/
- **mainbyte.com, TI-99 Extended BASIC** - http://mainbyte.com/ti99/software/s_carts/ext_basic.html

### C. Toolchain behaviour

- **`xas99.py` line 1537 and `xga99.py` line 960** - the extension search lists. These are the authority for `.a99` and `.g99` being xdt99 conventions rather than inventions, and for `.asm`, `.gpl`, `.s`, `.g` as accepted alternates.

### D. Native files and containers

- **TIFILES 128-byte header layout** - required before any tokenized program taken off a disk can be parsed. Verified empirically against Classic99 FIAD output during this work. A primary written source should be added to the bibliography; the behaviour is currently evidenced only by our own fixture, `test/fixtures/xb-tifiles.prg`.

### L. Emulator behaviour

- **Classic99 auto-run behaviour for DSK1.LOAD** - no written source found. Established experimentally and recorded in `docs/basic-support-design.md` section 1.9: standard PROGRAM auto-runs, long INT/VAR 254 does not. If a documented source exists it should replace the experiment as the citation, but the experiment is reproducible from a cold start.

### Q. VS Code platform

- **Submenus** - https://code.visualstudio.com/api/references/contribution-points#contributes.submenus
- **when clause context keys** - https://code.visualstudio.com/api/references/when-clause-contexts
- **Language configuration guide** - https://code.visualstudio.com/api/language-extensions/language-configuration-guide
- **Syntax highlight guide** - https://code.visualstudio.com/api/language-extensions/syntax-highlight-guide - needed for the missing BASIC grammars.
- **Testing extensions** - https://code.visualstudio.com/api/working-with-extensions/testing-extension - needed for the two untested acceptance items.

### New group: test tooling

- **Node.js built-in test runner** - https://nodejs.org/api/test.html - the whole suite uses it, with zero test dependencies. It requires Node 22 for glob patterns, which caused a CI failure earlier in development and is worth recording so it is not rediscovered.

### Methodological note

Extension adoption figures quoted during the naming research came from GitHub code search (`gh api search/code`), counting files by extension in TI-99 context. That API rate-limits aggressively. The figures were `.a99` 146, `.xb` 3, `.b99` 0 to 1, `.xb99` 0, `.g99` 0. They are indicative, not authoritative: GitHub code search covers only indexed public repositories.

## 10. Summary for planning

The assembly product is finished and verified. The naming and routing architecture is finished and heavily tested. The BASIC work has a solid foundation, a correct and well-tested dialect model, and no executable pipeline.

The next unit of work that changes what a user can actually do is the parser, followed by making BASIC a project language so that the tokenisation which already exists becomes reachable. Everything else in phase 1 depends on those two.

The three P0 items are small and should go first, because each one is a place where the product currently promises more than it delivers.
